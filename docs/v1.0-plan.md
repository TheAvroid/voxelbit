# voxelbit v1.0 — Pixel Streaming Plan

_Status: planning. Prep begins **August 2026**. Current shipping build: v0.9 (pine forest, client-side JS engine `engine.html`)._

## Decision

**Deliver the game via pixel streaming (cloud gaming).** `engine.html` runs **unchanged** on your server GPUs; each player's browser receives a live video stream and sends input back. Chosen over the Rust/WASM rewrite because it needs **no rewrite** — you keep the HTML/JS engine and the single-file workflow — and gives **total** code protection (the client only ever receives video).

**What this means:**
- **No engine rewrite.** `engine.html` runs as-is on the server.
- **Client = thin WebRTC video player** (~5 KB), zero game code, zero shaders, zero assets.
- **Total protection** — nothing readable ever reaches the player.
- **Forces monetization.** Every player-hour costs *you* GPU money, so the game can no longer be free — revenue must cover the servers. This is a core constraint, not a footnote.
- **Streaming-only.** To protect the code you can NOT also ship the free local browser build (that would leak the very code you're protecting). So all players get the streamed experience (see caveats).

## Architecture

```
  PLAYER BROWSER                          YOUR GPU FLEET (per session)
 ┌──────────────┐   WebRTC video/audio   ┌─────────────────────────────┐
 │ thin client  │ <───────────────────── │ headless Chromium + real GPU│
 │ (video + a   │                        │   └─ engine.html (UNCHANGED) │
 │  little JS)  │ ──────────────────────>│   canvas → NVENC → WebRTC    │
 └──────────────┘   input datachannel    └─────────────────────────────┘
        │                                          ▲
        │ signaling / auth / "give me a session"   │ spin up / tear down
        ▼                                          │
 ┌──────────────────────────────────────────────────────┐
 │ Signaling + Session Orchestrator + Auth + TURN + Pay  │
 └──────────────────────────────────────────────────────┘
```

The public site stops serving `engine.html`; it serves only the thin client + signaling. The engine + assets live only inside the GPU container image, behind auth.

## The one risk that can kill this — validate FIRST

Your own notes: **"no `--headless` (no WebGPU adapter)"** and *"CDP window must be offscreen."* That's the wall you'll hit on a server. WebGPU needs a real Vulkan-capable adapter; naive headless Chrome exposes none. On a Linux GPU box you get it via a real Xorg + NVIDIA driver + a dummy/offscreen display, then Chrome with `--use-angle=vulkan --enable-features=Vulkan` — **not `--headless`**. **Until voxelbit is proven to render at framerate in that server config, nothing else matters.** Phase 0 is a pure spike on exactly this.

## Phased build

- **Phase 0 — WebGPU-on-server spike (existential go/no-go).** One cloud GPU box (NVIDIA L4/A10). Xorg-dummy + NVIDIA driver, Chrome offscreen with Vulkan/ANGLE, load `engine.html`, confirm via your CDP harness it renders at framerate. Deliverable: a screenshot + fps number from the server.
- **Phase 1 — single-session streaming PoC.** That box streams the canvas to one browser. Building block: **Selkies-GStreamer** (containerized GPU → WebRTC, NVENC hardware encode) or `webrtcbin` + `nvh264enc`. Avoid the browser's own `canvas.captureStream` WebRTC — it won't reliably use NVENC.
- **Phase 2 — input, audio, latency.** Relay keyboard/mouse/**pointer-lock** (critical for mouse-look) + game audio over a datachannel; tune bitrate/resolution/encoder for the input→photon budget. **Make-or-break** — a first-person game feels bad above ~60–80 ms round trip. Test from real player locations.
- **Phase 3 — orchestration.** One GPU process per concurrent player; queue when the fleet is full; reap idle sessions aggressively (they bill every second).
- **Phase 4 — auth, saves, cost guardrails, PAYWALL.** Login gates GPU spend; persist each player's world; hard idle timeouts + concurrency caps; and the **monetization layer** (below), without which the economics don't close.
- **Phase 5 — cutover.** Replace `engine.html` at the site root with the thin client; scrub the engine + assets from every public path. View-Source now yields a video player.
- **(Parallel / later) Teardown destruction.** Built in the JS engine and run on the server GPU. Running on controlled, powerful hardware makes heavy physics *more* feasible than on arbitrary client machines — but it's still a large, separate build (mutable/chunked world model, `rapier.js`/`ammo.js`, debris via the trace-injection pipeline, BOUNDED persistence). NOT part of the August streaming milestone.

## Monetization — required, not optional

Pixel streaming means you pay per player-hour, so the game **must** earn to cover it:
- **Subscription** (monthly, GeForce-NOW style) — most predictable revenue vs. cost.
- **Paid access / one-time unlock** — simpler, but ongoing server cost with one-time revenue is risky.
- **Hourly credits / metered** — directly maps price to your cost.
Model **price ≥ your blended cost per player-hour** with margin, before committing.

## Cost model (the number that decides viability)

Per-player-hour, and it **scales up with success**:
- ~$0.30/player-hour blended estimate.
- Average **10 concurrent 24/7** ≈ **~$2,200/month**; **50 concurrent** ≈ **~$11,000/month**.
- 100 concurrent players ≈ 25–100 live GPUs.
Model this against expected concurrency **and** your monetization price *before* Phase 1.

## Tech stack

- **Web layer: SvelteKit** (chosen, replaces PHP). One modern full-stack framework for the whole "front door": the thin video-player client, the signaling/session API (WebRTC offer/answer + "give me a session"), auth/accounts, and the paywall/billing pages. Deploys as a Node app (or to the edge); server routes handle the API, `+page` routes the UI.
- **GPU fleet:** cloud (AWS `g6`, GCP `g2`) or self-hosted NVIDIA (L4/A10 or a consumer RTX box for the pilot). Cloud = faster start; self-host = cheaper at scale, more ops.
- **Streaming:** Selkies-GStreamer, or `webrtcbin` + `nvh264enc`/`nvav1enc` for more control. NVENC hardware encode (prefer AV1 on RTX 40/50-series to cut bandwidth).
- **Session:** SvelteKit server routes for signaling + an orchestrator (allocate/queue/reap GPU sessions) + TURN (NAT traversal).
- **The engine:** `engine.html` unchanged, in a headless-GPU Chromium container.

## August 30-day gameplan

**Definition of done (Aug 31):** one player can stream voxelbit from a server GPU to a browser and play it smoothly, with input + audio, at an acceptable latency — i.e. Phases 0–2 proven. Orchestration/scaling/auth/paywall/cutover are September+.

- **Week 1 — Phase 0 spike.** Rent a cloud GPU; stand up Xorg-dummy + NVIDIA + Chrome-Vulkan offscreen; prove `engine.html` renders at framerate via CDP. **Go/no-go for the whole strategy.**
- **Week 2 — Phase 1 PoC.** Selkies-GStreamer (or `webrtcbin`+NVENC): stream the canvas to one browser. Get moving video on a remote machine.
- **Week 3 — Phase 2 input + audio + latency.** Relay keyboard/mouse/pointer-lock + audio; tune the encoder; measure input→photon latency.
- **Week 4 — harden + measure + decide.** Test latency/quality/data-use from **real player locations** (not next to the server); measure cost per session; decide the **monetization model + price**. Write up done/next.

**Risk note:** if Phase 0 fails (WebGPU won't render on the server GPU), the whole strategy is blocked — which is why it's Week 1. Fallback if latency (Phase 2) proves unacceptable from real locations: the plan reverts to "accept visible source" or the Rust rewrite.

## Honest caveats (decide with eyes open)

- **Forever cost + forced monetization** — a free voxelbit is off the table under this plan.
- **Latency is permanent** — if it feels bad from real locations, that doesn't improve.
- **Compression artifacts hit voxelbit hard** — video codecs smear high-frequency detail in motion (foliage, snow, grain, sparkle) — exactly your aesthetic.
- **All players get a worse experience than today's free local render** — and you can't offer the free local build alongside (it would leak the code). Everyone is on the stream.
- **TDR / device-loss on the server** can drop live (paying) sessions — the same class as the `gpu device lost` bug; frame stability matters even more now.

## Open decisions

1. **Cloud vs. self-hosted GPUs** — changes the whole ops stack.
2. **Expected peak concurrent players** — drives cost model + queue.
3. **Monetization model + price** — subscription vs. metered; must exceed cost-per-player-hour.
4. **Destruction in v1.0 or deferred?** — it's a separate large build on top of the streaming work.
